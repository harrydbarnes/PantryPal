# Bug audit — 27 October 2026

## Executive summary

This is a targeted initial review, not a complete repository audit. One high-priority household sync integrity defect was identified and fixed on branch `fix/firestore-protocol-downgrade`. The fix passed the Firestore emulator suite but has not been deployed. No claim is made that other areas are free of defects.

## BUG-001 — Protocol 4 can be reset to protocol 3

- **Severity / priority:** High / P1; **category:** integration, data integrity; **component:** Firestore household sync rules.
- **Files:** `firebase/firestore.rules`, `firebase/rules.test.mjs`.
- **Current behavior:** An authenticated household member can update a protocol 4 state to protocol 3 migration, resetting its revision to zero. The old rule accepts every prior protocol except 3.
- **Expected behavior:** Only legacy protocol 1 or 2 state can enter protocol 3 migration; protocol 4 cannot be downgraded.
- **Root cause:** The migration guard used `protocol != 3` instead of restricting the allowed source versions.
- **Impact:** A member using a direct Firestore request or a faulty client can disrupt the shared shopping sync protocol and its revision history; potential data loss or inconsistent synchronization requires runtime confirmation. This requires household membership, not anonymous access.
- **Reproduction:** With the Firestore emulator and test dependencies installed, create a household, move its state to protocol 4 ready, then submit an authenticated state update setting protocol 3, phase migrating, revision 0 and valid author fields. The original rules allow it; the proposed rules should reject it. `protocol 4 cannot be reset to protocol 3 migration` encodes this scenario.
- **Fix:** Restrict the migration source to protocols 1 and 2, retaining the existing default for a missing legacy protocol. Complexity is low; deployment requires normal rules review and emulator validation.
- **Verification status:** The new regression failed against a temporary copy of the original rules because the downgrade succeeded. All 8 Firestore emulator tests passed with the corrected rules. JavaScript syntax and `git diff --check` also passed. The rules have not been deployed.

## Coverage and remaining work

The review examined the sync rules, relevant test structure, and portions of backup and shopping repository code; it did not exhaustively trace all paths or establish test coverage. Android unit tests and lint could not start because Gradle failed to establish a loopback connection, including outside the sandbox. `npm audit` could not run at the time because the Firebase project had no lockfile. No Android dependency vulnerability scan or performance benchmark was completed. Run Android unit/instrumented tests and lint, scan both dependency graphs, and continue the repository-wide review before treating the audit as complete.

## Prevention

Model allowed protocol transitions as an explicit allowlist and add negative tests for every newer protocol and migration phase. Run the rules emulator suite in CI and maintain a reproducible dependency lockfile so dependency audits can run. Monitor rejected sync transitions and migration failures without logging household invite codes or shopping contents. Review any future protocol changes for backward compatibility and version the public API when its contract changes.
